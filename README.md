# MDC HUB V5

A cyber-luxury Roblox script discovery interface built with React 19, TypeScript, Vite and Tailwind CSS 4.

## Overview

MDC HUB pulls a live, categorized script catalog from ScriptBlox on the server side and serves it as static JSON on GitHub Pages. The browser never calls the source API directly, so the catalog works without client-side CORS issues or exposed API keys.

- **Source:** ScriptBlox (`/api/script/fetch`, `/api/script/trending`, `/api/script/:slug`)
- **Categories:** Trending, New, Popular, Keyless, Universal, Verified, Patched
- **Refresh:** GitHub Actions runs every six hours and on manual dispatch.
- **Fallback:** If sync fails, the last JSON stays live; if no JSON is available, the site falls back to the curated local selection.
- **Safety:** Third-party code is displayed and copied, never executed. Every external script links back to its source and shows a license/safety notice.

### Optional Rscripts source

Rscripts requires an API key. To merge its catalog into the same categories, add a repository Actions secret named `RSCRIPTS_API_KEY`. The key is used only inside the workflow; it is never sent to the browser.

## Internationalization

The interface auto-detects the browser language:

- Turkish browsers get Turkish.
- Every other language falls back to English.
- The choice can be changed with the language button in the header and is remembered in `localStorage`.

UI copy, category names, dates and compact numbers are localized. Script titles, descriptions, tags and source labels from third-party catalogs remain in their original language.

## Local development

```bash
npm ci
npm run dev
```

Vite uses `dev.html` as the source entry. `http://localhost:3000/` redirects to `/dev.html`.

```bash
npm run sync:scripts   # Fetch ScriptBlox data into public/data/scripts.json
npm run build          # Typecheck and build dist/
npm run build:pages    # Build with the /MDC-HUB-V5/ base and publish root files
```

## GitHub Pages

`index.html`, `assets/`, `favicon.svg`, `.nojekyll` and `data/` are generated by
`npm run build:pages`. Do not edit the root `index.html` or `assets/` by hand; edit
`dev.html` and `src/` instead.

The workflow `.github/workflows/deploy-pages.yml` runs on every push to `main` and
on a six-hour schedule. It:

1. Refreshes ScriptBlox data (failures keep the previous catalog),
2. Builds the site and publishes the root files,
3. Commits the refreshed catalog and generated build with `[skip ci]`,
4. Uploads the Pages artifact and deploys it.

This keeps the site working whether the repository Pages source is set to
**Deploy from a branch (main / root)** or **GitHub Actions**. Generated commits do
not re-trigger the workflow.

The current build is configured for the project path `/MDC-HUB-V5/`. A custom
domain at the site root requires rebuilding with a `/` base path.

## Accounts (Cloudflare + Discord)

Accounts run on a Cloudflare Worker with a D1 database and Discord OAuth. The
static site only renders the interface; it never holds the Discord client secret.

- **Sign-in:** Discord OAuth 2.0 with the `identify` scope only. Browse your
  profile with no email, password or SMTP provider.
- **Session:** an opaque 256-bit bearer token stored in `localStorage`; D1 keeps
  only its SHA-256 hash. Sessions use a 30-day sliding expiry and are revoked on
  sign-out.
- **Why bearer instead of cookies:** `github.io` and `*.workers.dev` are different
  sites, so third-party cookies are blocked by several browsers. An
  `Authorization` header works on every browser without weakening cookie policy.
- **CORS:** the Worker answers only the origins listed in `SITE_ORIGINS`.
- **Roles:** every new account is a `member`; Discord ids listed in
  `ADMIN_DISCORD_IDS` are upgraded to `admin` on sign-in.

### 1. Create the Discord application

1. Open <https://discord.com/developers/applications> and create an application.
2. Under **OAuth2**, copy the **Client ID** and **Client Secret**.
3. Add the redirect URI `https://<worker-name>.<subdomain>.workers.dev/auth/discord/callback`
   (plus `http://127.0.0.1:8787/auth/discord/callback` for local development).
4. Keep the scope at `identify`; no email scope is requested.

### 2. Create the D1 database

```bash
npx wrangler login
npx wrangler d1 create mdc-hub
```

Copy the returned `database_id` into `worker/wrangler.jsonc`, replacing the
all-zero placeholder. Set `DISCORD_CLIENT_ID` in the same file.

### 3. Store the secret, migrate and deploy

```bash
npx wrangler secret put DISCORD_CLIENT_SECRET --config worker/wrangler.jsonc
npm run db:migrate:remote
npm run worker:deploy
```

`worker:deploy` prints the public `*.workers.dev` URL.

### Deploying from GitHub Actions (no local terminal)

`.github/workflows/deploy-api.yml` can deploy the Worker and apply D1 migrations
on GitHub's runners. Add these repository secrets under **Settings → Secrets and
variables → Actions**:

- `CLOUDFLARE_API_TOKEN` — API token with *Workers Scripts:Edit*, *D1:Edit* and
  *Account Settings:Read*.
- `CLOUDFLARE_ACCOUNT_ID` — the account id shown on the Workers & Pages overview.

Run **Deploy API (Cloudflare Worker)** from the Actions tab. The run summary
prints the Worker URL and the exact Discord redirect URI. The job skips itself
until `worker/wrangler.jsonc` has a real D1 id and Discord client id. The Discord
client secret is added once in the Cloudflare dashboard, not in GitHub.

### 4. Point the site at the API

Edit `public/config.json` (served at runtime, no rebuild of the app code needed):

```json
{ "apiBaseUrl": "https://mdc-hub-api.<your-subdomain>.workers.dev" }
```

Commit and push so the Pages workflow republishes it. Until this value is set,
the login dialog shows a setup notice instead of failing silently.

### Local development

```bash
npm run db:migrate:local   # create the local D1 tables
npm run worker:dev         # API on http://127.0.0.1:8787
npm run dev                # site on http://localhost:3000, targets :8787 in dev
```

Put local Discord credentials in `worker/.dev.vars` (see
`worker/.dev.vars.example`). The site only uses the local fallback in development
builds; Pages builds always read `config.json`.

### API surface

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/health` | API, D1 and Discord configuration status |
| `GET` | `/auth/discord` | Starts Discord OAuth (sets the state cookie) |
| `GET` | `/auth/discord/callback` | Validates state, reads the profile, issues a one-time code |
| `POST` | `/auth/exchange` | Exchanges the one-time code for a bearer token |
| `GET` | `/api/me` | Returns the signed-in profile |
| `POST` | `/auth/logout` | Revokes the current session |

See [worker/README.md](worker/README.md) for troubleshooting.

## Safety model

- Script code is rendered as text and copied to the clipboard; it is **never
executed** in the browser.
- External links use `rel="noopener noreferrer"` and only `http(s)` URLs are
  accepted.
- Every third-party script keeps a visible source label and links back to its
  original page.
- The catalog is fetched by GitHub Actions, not by the browser, so no API keys
  or credentials are shipped to visitors.
- If the catalog cannot be refreshed, the last published JSON is retained; the
  build does not invent or promote unreviewed scripts.
- Account data lives in D1 behind the Worker. The browser never receives the D1
  binding or the Discord client secret, and every account query is scoped to the
  session owner.
- OAuth uses a single-use `state` value bound to an HttpOnly cookie, and login
  codes are single-use, hashed at rest and expire after 60 seconds.
- Session tokens are bearer credentials: any XSS would expose them. The app only
  renders third-party script code as escaped text and never executes it, but a
  strict Content Security Policy still needs to be added at the CDN/host layer
  because GitHub Pages cannot set response headers.
